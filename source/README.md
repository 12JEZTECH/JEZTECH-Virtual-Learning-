# ExamGuard

A hosted exam system with an HTML interface, verified ChatGPT sign-in, server-side role checks, a shared D1 database, and live status polling. This replaces the previous browser-local demonstration. Existing localStorage demo records are not imported into the shared database.

## Getting started

The verified Site owner is enrolled as the administrator on first sign-in. Create an exam, add its multiple-choice questions and optional schedule, then publish it. Invite additional accounts with the Site's sharing settings. Each invited user initially receives the student role. After their first sign-in, an administrator can promote their account to teacher in People & access. Disabling an account blocks API access; changing an application role does not change Site sharing.

Teachers manage their own exams and sessions. Administrators can manage all exams, sessions, and registered accounts. Students receive published exams and their own attempts and results. Correct answer keys are never returned to students. Only student accounts can take assessments.

## Assessment lifecycle

Each student has one attempt per exam. Answers save to the server and can be resumed after reload. The server enforces the deadline and calculates scores. Teacher pause preserves remaining time; resume restores it, capped by a scheduled closing time. Closing an exam stops new attempts and lets ongoing attempts finish. Published and closed question banks are immutable. Server expiry is finalized on the next API request and scored from saved answers. A client that closes the page cannot extend its deadline.

Browser presence heartbeats run every 10 seconds; views refresh every 4 seconds. The system logs focus, tab visibility, copy/paste, and fullscreen exit events. These are browser-reported signals and can be disabled or fabricated by a modified client. Flags require human review; events never automatically terminate a session. Optional face checks use the supplied face-api library and detector model from a pinned jsDelivr URL. Camera processing runs locally. Only no-face, multiple-face, and off-centre event flags are sent to the server. Images, audio, and video are not uploaded. Detector availability and accuracy depend on the browser and network; this is not identity verification or a video call.

## Implementation

- `app/service.ts`: validated actions, ownership checks, D1 operations, server deadlines and grading.
- `app/api/workspace/route.ts`: identity, origin and JSON validation, private API.
- `app/workspace.tsx`: teacher, student and administrator interfaces.
- `db/schema.ts` and `drizzle/`: database schema and migrations.
- `tests/service.test.mjs`: SQLite integration tests using the same SQL service.

The provided Express/Socket.IO and PostgreSQL snippets served as the domain reference. Hosted code uses Workers-compatible requests, D1 and polling rather than an Express server, raw PostgreSQL connections, or Socket.IO. No custom passwords or JWT keys are required. Authentication belongs to the hosting platform. The verified owner email is used for initial administrator enrollment; existing account roles remain stored in the database.

## Ten-minute class preparation and learner board

## Automatic payment integration — requires live operator setup

`/api/payments` implements live Daraja STK initiation and authenticated server-side STK status queries. Prices and access days are snapshotted from the admin plan, not accepted from the browser. A pending request alone never unlocks access. Only a matching provider-confirmed successful checkout creates the verified subscription. The D1 grant is idempotent, renewals extend existing paid access, and the learner ID and one-time video credit are issued automatically. The activation/payment panel checks pending payments every twelve seconds; the existing authenticated assistant maintenance route also reconciles pending payments while learners are away. Raw callbacks and typed receipts are not trusted as proof of payment.

**Automatic recording requires a configured live connection.** Runtime configuration is checked by the administrator payment panel and the public health readiness field; secret presence alone does not establish provider connectivity. No real payment was initiated or charged during development. Provider responses were simulated in automated tests; a real end-to-end payment still needs testing after approved setup. The UI reports **Setup required** until the required runtime configuration exists. Existing manual statement verification remains available for direct Paybill transfers.

Configure through the Site's secure production runtime settings, never source code or chat:

- `MPESA_CONSUMER_KEY` and `MPESA_CONSUMER_SECRET`: live Daraja application credentials for the approved collection account (secrets).
- `MPESA_PASSKEY`: live M-Pesa Express passkey (secret).
- `MPESA_SHORTCODE`: approved collection shortcode, currently constrained to the owner's configured Paybill `522533`.
- `MPESA_CALLBACK_URL`: the operator-approved public HTTPS callback receiver. The public Site provides `/api/payments/callback` for bounded, untrusted JSON delivery. A matching checkout and merchant ID persist a callback hint and schedule an independent authenticated status query in the Worker background. Verification failures remain pending with an admin-visible retry count. Queries independently verify the checkout; callback content does not grant access.
- `MPESA_LIVE_ENABLED`: `true` only after the collection operator authorizes the live integration.

Preserve all existing runtime values, including `WORKSPACE_SERVICE_TOKEN`, and deploy a saved version after applying environment changes. The account reference remains `8075575`, recipient entered by the owner as JEZTECH ENTERPRISES. If this is an account under a bank/aggregator's shared Paybill, obtain the collection operator's supported merchant integration; an unrelated personal Daraja application does not establish access to that Paybill. This implementation does not automatically reconcile arbitrary direct Paybill transfers. For confirmed STK payments, the stored reference `STK:<CheckoutRequestID>` is a real provider checkout reference, not an invented M-Pesa receipt number. Reconcile any manual receipt against operator records to avoid crediting the same payment twice.

Primary implementation references: [Safaricom M-Pesa Express](https://developer.safaricom.co.ke/apis/MpesaExpressSimulate), [Safaricom SDK STK query](https://github.com/safaricom/mpesa-php-sdk/blob/master/src/Mpesa.php), [Safaricom Authorization](https://developer.safaricom.co.ke/apis/Authorization).
